# Анализ безопасности системы Медикаменте — Task 1

## 1. Список проблемных зон (As-Is анализ)

### 1.1 Критические проблемы

#### P1.1: Отсутствие шифрования данных
- **Проблема:** Все конфиденциальные данные (медицинские карты, ПИИ пациентов, финансовая информация) хранятся в открытом виде в Excel, PDF, JPG файлах без шифрования.
- **Импакт:** Любой сотрудник с доступом к файловому серверу может читать все медицинские данные; риск утечки при компрометации сервера.
- **Требование:** Федеральный закон РФ 152-ФЗ требует защиты ПИИ граждан.
- **Рекомендация:** Шифрование at-rest (AES-256) для всех файлов с ПИИ; использование DPAPI или аналога.

#### P1.2: Отсутствие контроля доступа (RBAC/ABAC)
- **Проблема:** Нет дифференцированного доступа к данным. Ограничение только на уровне доменной аутентификации (Active Directory). Кассир имеет доступ к медицинским картам; специалист — к финансовым данным платежей других пациентов.
- **Импакт:** Нарушение принципа наименьших привилегий; легко происходит несанкционированный доступ внутри организации.
- **Требование:** Privacy by Design.
- **Рекомендация:** Внедрить RBAC (5 базовых ролей: Admin, Specialist, Reception, Patient, Accountant) или ABAC с атрибутами (department, patient_id, data_classification).

#### P1.3: Отсутствие аудита и логирования
- **Проблема:** Результаты работы с данными сохраняются в файлах без аудита действий. Невозможно отследить, кто, когда, что открыл, изменил или скопировал.
- **Импакт:** Невозможно провести forensics при утечке; нарушение требований ГОСТ по аудиту; репутационный риск при проверке регуляторами.
- **Требование:** Сохранение логов для возможности расследования.
- **Рекомендация:** Централизованное логирование всех событий доступа к ПИИ (who/what/when/where/result) в неизменяемый лог; минимум 1 года истории.

#### P1.4: Отсутствие классификации данных
- **Проблема:** Нет разделения данных по уровню конфиденциальности. Все данные хранятся вместе: базовые ПИИ (ФИО, телефон), расширенные (адрес, хроническое заболевание), медицинские (диагнозы, анализы), финансовые.
- **Импакт:** Избыточное накопление ПИИ нарушает принцип Data Minimization; сложнее защитить все одинаково.
- **Требование:** Privacy by Design требует классификации данных перед обработкой.
- **Рекомендация:** Определить 4 класса: PUBLIC, INTERNAL, CONFIDENTIAL, RESTRICTED; применить разные уровни защиты для каждого.

### 1.2 Высокие проблемы (ВЫСОКИЙ ПРИОРИТЕТ)

#### P2.1: Ручная обработка данных — ошибки и утечки
- **Проблема:** Все операции с данными выполняются вручную (ввод в Excel, копирование между системами). Сотрудники распечатывают медицинские карты, отправляют по почте, хранят на рабочем столе.
- **Импакт:** Высокий риск случайного раскрытия ПИИ (распечатанные карты в офисе, копии по email, забытые на принтере).
- **Требование:** Privacy by Design.
- **Рекомендация:** Автоматизировать обработку; минимизировать ручные операции; использовать утвержденные каналы передачи (шифрованный email, защищённый портал).

#### P2.2: Интеграция 1С в файловом режиме
- **Проблема:** 1С:Бухгалтерия и 1С:Торговля работают в файловом режиме. Финансовые данные и данные об ТМЦ передаются через копию файлов на сетевой диск без шифрования.
- **Импакт:** Нет изоляции; любой сотрудник с доступом к диску видит все платежи, контракты, ценообразование.
- **Требование:** Separation of concerns, RBAC.
- **Рекомендация:** Переход на сетевой режим 1С с использованием VPN; API-интеграция вместо файлового обмена; шифрование в-транзит (TLS 1.3).

#### P2.3: Отсутствие контроля целостности данных
- **Проблема:** Excel файлы могут быть изменены без истории версий. Нет механизма обнаружения несанкционированного изменения данных (например, кто-то изменил диагноз или цену услуги).
- **Импакт:** Риск подделки медицинских записей; нарушение целостности финансовых данных.
- **Требование:** Обеспечение целостности ПИИ.
- **Рекомендация:** Использовать СУБД вместо Excel с ACID гарантиями; технология цифровой подписи или HMAC для проверки целостности.

#### P2.4: Отсутствие Data Lineage / Трассировки данных
- **Проблема:** Неясно, откуда берутся данные о пациенте, как они трансформируются, в каких системах хранятся, кто получал доступ.
- **Импакт:** При запросе пациента на удаление данных (право на забывчивость) невозможно отследить все копии.
- **Требование:** Закон 152-ФЗ,Data Lineage.
- **Рекомендация:** Введение системы тегирования; отслеживание в каких системах какие данные пациента; ведение реестра обработки.

### 1.3 Средние проблемы (СРЕДНЕЕ ЗНАЧЕНИЕ)

#### P3.1: Отсутствие технологии tokenization/pseudonymization
- **Проблема:** При разработке BI/ML систем разработчики работают с реальными медицинскими данными, адресами, телефонами пациентов.
- **Импакт:** Расширение круга лиц с доступом к реальным ПИИ; риск утечки при работе на ноутбуке разработчика.
- **Рекомендация:** Для non-prod окружения использовать анонимизированные/обезличенные данные или pseudonymization (заменить реальные значения на сгенерированные, но сохранив структуру).

#### P3.2: Отсутствие резервного копирования с шифрованием
- **Проблема:** Резервные копии могут быть унесены, украдены; неясно, где они хранятся, есть ли доступ.
- **Импакт:** Риск восстановления украденных данных; невозможность восстановления после ransomware.
- **Рекомендация:** Резервные копии с шифрованием; георедундантное хранилище; отдельная система управления резервными копиями.

#### P3.3: Отсутствие мониторинга аномалий
- **Проблема:** Нет системы, которая заметит, если один пациент скачал данные 1000 других пациентов или специалист работает в 3 ночи с базой платежей.
- **Импакт:** Несанкционированный доступ остаётся незамеченным; нарушение требования о своевременном обнаружении инцидентов.
- **Рекомендация:** Система мониторинга и алертинга (SIEM) для обнаружения аномалий в логах доступа.

## 3. Процессы в компании, подвергаемые анализу

### Процесс 1: Прием пациента и запись
- **Участники:** Пациент → Ресепшен
- **Данные:** ФИО, ДР, телефон, email, расширенные данные (адрес, место работы, хронические заболевания)
- **Текущий поток:** Ручной ввод в Excel → Сохранение на файловый сервер
- **Уязвимости:** Нет шифрования, нет RBAC, нет аудита

### Процесс 2: Медицинский осмотр и диагностика
- **Участники:** Пациент → Медицинский специалист
- **Данные:** Диагноз, результаты анализов, рекомендации, рецепты
- **Текущий поток:** Ручное заполнение медицинской карты (Excel/PDF/JPG) → Сохранение на файловый сервер
- **Уязвимости:** Нет шифрования, нет классификации (все данные вместе), нет целостности

### Процесс 3: Оплата услуг
- **Участники:** Пациент → Кассир → Бухгалтерия
- **Данные:** Платёжные данные (сумма, вид услуги), реквизиты пациента, реквизиты счета
- **Текущий поток:** ККМ → 1С:Бухгалтерия (файловый режим) → Excel учёт → Файловый сервер
- **Уязвимости:** Файловый режим 1С, нет шифрования передачи, ручной ввод в Excel

### Процесс 4: Управление товарно-материальными ценностями
- **Участники:** Склад → Бухгалтерия
- **Данные:** Количество, цена, поставщик, статус закупки
- **Текущий поток:** 1С:Торговля (файловый режим) → Синхронизация с 1С:Бухгалтерия
- **Уязвимости:** Файловый режим 1С, нет защиты при передаче файлов

### Процесс 5: Интеграция с лабораторией анализов
- **Участники:** Лаборатория (внешняя) → 1С
- **Данные:** Результаты анализов, ПИИ пациента, медицинские данные
- **Текущий поток:** Не определён (планируется)
- **Требования:** API-контракты должны скрывать ПИИ других пациентов; предотвращение чтения данных других пациентов

## 4. Выводы и рекомендации по приоритизации

**Фаза 1 (Критично — 3-4 недели):**
1. Внедрить классификацию данных (4 класса)
2. Внедрить RBAC с минимум 5 ролями
3. Начать логирование доступа к данным (аудит)
4. Внедрить шифрование для критических данных at-rest (AES-256)

**Фаза 2 (Высокий приоритет — 5-6 недель):**
5. Шифрование in-transit (TLS 1.3 для всех сетевых взаимодействий)
6. Контроль целостности данных (HMAC, цифровая подпись)
7. Data Lineage система (тегирование, реестр обработки)
8. Переход 1С на сетевой режим / API интеграция

**Фаза 3 (Средний приоритет — 7-8 недель):**
9. Токенизация/обезличивание для non-prod окружений
10. Защита резервных копий
11. Система мониторинга аномалий (SIEM)
