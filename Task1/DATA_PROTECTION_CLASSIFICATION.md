## 3. Инструменты и методы защиты по категориям данных

### 3.1 Шифрование at-rest (покоящихся данных)

| Уровень | Класс данных | Алгоритм | Управление ключами | Реализация |
|---|---|---|---|---|
| **CONFIDENTIAL** | Базовые и расширённые ПИИ | AES-256 GCM | DPAPI (Windows) + HSM для production | Windows EFS или Database-level encryption (PostgreSQL pgcrypto) |
| **RESTRICTED** | Диагнозы, анализы, платежи | AES-256 GCM + AEAD | Аппаратный HSM (Hardware Security Module) | Database encryption (TDE in SQL Server / pgcrypto in PostgreSQL) + TDE для Excel → Database migration |
| **Резервные копии** | Все критичные данные | AES-256 GCM | Отдельный ключ в HSM; ротация раз в год | Инкрементальные encrypted backups в облако (Yandex Cloud Backup или AWS S3 + encryption) |

### 3.2 Шифрование in-transit (в движении)

| Канал связи | Протокол | Сертификат | Реализация | Примечания |
|---|---|---|---|---|
| **Клиент ↔ Сервер** | TLS 1.3 | X.509 (self-signed для prod, Let's Encrypt для внешних) | HTTPS на портале; encrypted email для уведомлений | Perfect Forward Secrecy (PFS) обязателен |
| **1С ↔ Сервер** | TLS 1.3 или VPN | Сертификат компании | VPN tunnel (OpenVPN или Wireguard) для безопасности file-sharing | 1С файловый режим → сетевой режим с TLS |
| **API к лаборатории** | TLS 1.3 + mTLS | X.509 (client certificate) | Взаимная аутентификация сертификатами; подпись запросов | API Gateway с rate limiting и WAF |
| **Email с ПИИ** | TLS + S/MIME или PGP | Сертификат отправителя | Шифрование конца-в-конца (E2E) для напоминаний с ПИИ | Уведомления с анонимными ссылками вместо ПИИ в теле письма |
| **Синхронизация между системами** | TLS 1.3 | X.509 | API-based synchronization вместо file-sharing | Аудит всех операций синхронизации |

### 3.3 Обфускация и маскирование данных

| Техника | Применение | Примеры | Когда использовать |
|---|---|---|---|
| **Маскирование** | Скрытие части данных при отображении | Телефон: +7(XXX)XXX-63-89; Карта: XXXX-XXXX-XXXX-1234 | UI, логи, уведомления |
| **Токенизация** | Замена реального значения на токен (case-specific) | Платёжные реквизиты: сохранить только токен в системе, реальное значение в Payment Gateway | Minimization ПИИ; PCI DSS compliance |
| **Обезличивание (Pseudonymization)** | Замена идентификатора на псевдоним, но сохранение возможности восстановления | ФИО и ДР → Patient_ID_12345 (восстановимо владельцем ключа) | Аналитика, ML-обучение, разработка |
| **Анонимизация (Anonymization)** | Необратимое удаление идентификатора | Удалить ФИО, дату рождения; оставить только "Пациент, 45 лет, мужской пол, диагноз гипертония" | Публичные отчёты, статистика |
| **Redaction** | Удаление чувствительных строк при экспорте | Удалить номер кредитной карты из PDF контракта при печати | Печать / экспорт документов |

### 3.4 Аудит и логирование

| Событие | Что логировать | Где хранить | Срок хранения | Осуществление |
|---|---|---|---|---|
| **Доступ к ПИИ пациента** | WHO (пользователь), WHAT (какие данные), WHEN (время), WHERE (IP/система), RESULT (успешно/отклонено) | Централизованная база (Elasticsearch + Kibana или Splunk) | 1 год (min); 3-7 лет для audit trail | На уровне СУБД + application-level logging |
| **Изменение ПИИ** | Кто, что было, что стало, когда, почему (если причина введена), digital signature | Immutable log (append-only, подпись каждой записи) | 7 лет (по закону 152-ФЗ) | Database triggers + application commit log |
| **Экспорт / Печать / Скачивание** | Пользователь, файл, размер, направление (email, printer, USB), время | Audit log + DLP система | 3 года | Integration с DLP (Data Loss Prevention) |
| **Административные действия** | Создание/удаление юзера, изменение ролей, изменение конфигурации | Admin audit log (отдельное хранилище) | 2 года | Logging middleware + admin console |
| **Отказы в доступе** | Пользователь, ресурс, время, причина отказа | Security log | 1 год | RBAC engine logging |

### 3.5 Целостность данных

| Метод | Применение | Примеры | Реализация |
|---|---|---|---|
| **HMAC (Hash-based MAC)** | Проверка, что данные не изменены в пути | API-запросы к лаборатории; синхронизация между системами | Подпись запроса: HMAC-SHA256(secret_key, body) в заголовке X-Signature |
| **Цифровая подпись (Digital Signature)** | Неотказуемость действия; гарантия авторства | Диагнозы врачей, рецепты, договоры | УКЭП (Усиленная Квалифицированная Электронная Подпись) для legal documents; код подписи врача в СУБД для внутренних |
| **Версионирование** | История изменений; восстановление | Все critical documents (контракты, диагнозы, платежи) | Database versioning (audit trail) + soft delete (обозначить как удаленное, но сохранить) |
| **Immutable Log** | Невозможно изменить или удалить; проверка цепи | Логи доступа к ПИИ | Append-only database table + cryptographic linking (следующая запись содержит hash предыдущей) |

### 3.6 Тегирование и классификация

| Компонент | Назначение | Примеры тегов | Инструмент |
|---|---|---|---|
| **Тегирование данных** | Пометить поля, содержащие ПИИ, для автоматического контроля | `tag:PII`, `tag:GDPR`, `tag:MEDICAL_SECRET`, `tag:FINANCIAL` | Custom metadata в СУБД или Data Catalog (Apache Atlas, Alation) |
| **Data Lineage** | Отследить, откуда берутся данные, где хранятся, кто обрабатывает | `source: PatientForm` → `storage: PostgreSQL.patients_db` → `usage: BI_report` | Data Lineage tool (Apache Atlas, Collibra, Informatica) |
| **PII Detection** | Автоматически найти возможные ПИИ (регулярные выражения + ML) | Detect email patterns, phone patterns, credit card patterns | Regex-based + ML (AWS Macie, Google DLP API, open-source like PII-masker) |
| **Classification Rules** | Автоматизировать классификацию при загрузке данных | IF contains(@email) THEN class=CONFIDENTIAL; IF MedicalKeywords THEN class=RESTRICTED | Data classification engine (custom Python или Microsoft Information Protection) |

## 4. Резюме инструментов защиты

### Стек технологий для защиты

**Шифрование:**
- At-rest: PostgreSQL pgcrypto или EFS (Windows)
- In-transit: TLS 1.3, OpenVPN/Wireguard для сетей
- Ключи: HSM (Yandex HSM или локальный Hardware Security Module)

**Контроль доступа:**
- RBAC: Custom role engine на уровне API
- Аутентификация: Active Directory (LDAP) + MFA (TOTP)
- Авторизация: Attribute-based policies (Open Policy Agent / Casbin)

**Аудит:**
- Логирование: ELK Stack (Elasticsearch + Logstash + Kibana) или Splunk
- Immutable logs: append-only PostgreSQL таблица с cryptographic linking
- Мониторинг аномалий: Sigma rules + SIEM alerts

**Data Governance:**
- Классификация: Custom classification engine + Apache Atlas для lineage
- Тегирование: Database metadata tags + Data Catalog
- DLP: Endpoint DLP agent + Network DLP

**Compliance:**
- Auditor role с доступом только к логам (нет доступа к данным)
- Annual security audit с external auditor
- Vulnerability scanning (OWASP ZAP для приложений + Nessus для инфраструктуры)
