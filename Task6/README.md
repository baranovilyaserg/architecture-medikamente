# Task 6: Движок классификации данных (Data Classification Engine)

### Проблема

Data Warehouse (Snowflake/BigQuery) в архитектуре To-Be содержит:
- **Частично классифицированные данные** (PII пациентов, медицинские записи)
- **Неструктурированный входящий поток** (данные из OLTP системы могут иметь переменную структуру)
- **Конфиденциальные поля** (диагнозы, результаты анализов, платёжная информация)

**Требование:** Реализовать **Privacy by Design** - автоматическая классификация и маскирование данных перед ETL загрузкой.

---

## Предлагаемое решение: Data Classification Engine

### Компоненты системы:
1. **Data Classification Engine:** Автоматическое обнаружение, классификация и трансформация данных на основе правил и ML-моделей.
2. **Data Classification Registry:** Хранилище метаданных о классификации (какие поля, какие правила применены, кто имеет доступ).
3. **ETL Pipeline Integration:** Классификация данных происходит в рамках ETL процесса, обеспечивая, что только безопасные данные попадают в DW.
4. **Access Control Layer:** Управление доступом к данным на основе их классификации (RBAC/ABAC).
5. **Audit & Lineage Tracking:** Логирование всех операций классификации и трансформации для обеспечения соответствия требованиям 152-ФЗ и GDPR.

---

## Компоненты Data Classification Engine:

### 1. **Auto-Discovery Layer**
- Сканирование таблиц/столбцов в OLTP
- Использует pattern matching (email@, phone +7, etc.)
- Сохраняет metadata в Data Classification Registry
- Триггер: Ежедневно, перед ETL запуском

### 2. **Classification Rules Engine**
- **Встроенные правила:**
  - `patient_name` → RESTRICTED (диагнозы, операции)
  - `phone` → CONFIDENTIAL (контактные данные)
  - `appointment_date` → INTERNAL (расписание)
  - `service_name` → PUBLIC (список услуг)

- **Custom rules** для доменов (Patients, Medical, Finance)
- **ML-based scoring** (опционально): entropy analysis для обнаружения неизвестных типов PII

### 3. **Слой преобразования (Transformation Layer)**
- **Для RESTRICTED:**
  - Хеширование персональных данных (SHA-256)
  - Медицинские данные токенизируются
  - Шифрование на уровне БД (TDE)

- **Для CONFIDENTIAL:**
  - Маскирование (только последние 4 цифры)
  - Обезличивание (UUID-based идентификаторы пациентов)
  - Очистка от временных меток

- **Для INTERNAL:**
  - Агрегирование (COUNT, SUM вместо сырых данных)
  - Удаление очень специфичных данных

- **Для PUBLIC:**
  - Прямой перенос или минимальная трансформация

### 4. **Метаданные и управление доступом (Metadata)**
- **Реестр классификации данных (Data Classification Registry):**
  - Таблица: `classification_metadata` (имя_таблицы, имя_колонки, уровень_классификации, применённое_правило)
  - Таблица: `transformation_audit_log` (временная_метка, колонка, правило, действие)

- **Управление доступом по классификации (Access Control by Classification):**
  - Слой 0 (Raw, RESTRICTED) → только DBA + Security команда
  - Слой 1 (CLEAN, CONFIDENTIAL) → Медицинские специалисты + аналитики
  - Слой 2 (CURATED, INTERNAL) → Все сотрудники
  - Слой 3 (PUBLIC) → Все + внешние консультанты

- **Отслеживание происхождения данных (Data Lineage):**
  - Отслеживание: OLTP колонка → Правило классификации → Слой DW → Отчёт BI
  - Используется для аудита соответствия (152-ФЗ: отследить каждый поток данных)

## Четыре слоя Data Warehouse для разных ролей:

| Слой | Классификация | Содержимое | Кто видит | Защита |
|------|---------------|-----------|----------|--------|
| **Слой 0 (RAW)** | RESTRICTED | Оригинальные данные из OLTP (зашифрованные) | DBA, CISO | Шифрование в покое + защита на уровне строк |
| **Слой 1 (CLEAN)** | CONFIDENTIAL | Персональные данные замаскированы (хеш), медицинские данные токенизированы | Врачи, аналитики | Шифрование + маскирование на уровне колонок |
| **Слой 2 (CURATED)** | INTERNAL | Агрегированные данные (без точного ПИИ), готовые к отчётам | Сотрудники | Стандартная безопасность |
| **Слой 3 (PUBLIC)** | PUBLIC | Агрегированная статистика (без ПИИ), открытые метрики | Все | Нет специальной защиты |

## Метрики эффективности классификации:

### 1. **Метрики охвата (Coverage Metrics):**
- % таблиц с определёнными правилами (целевое значение: 100%)
- % колонок с корректной классификацией (целевое значение: 98%+)
- Коэффициент обнаружения ПИИ: соотношение ложных срабатываний к пропускам

### 2. **Метрики качества (Quality Metrics):**
- Соответствие аудиту: все трансформации записаны логирован (100%)
- Целостность данных: правила валидации пройдены (99.9%+)
- Полнота отслеживания происхождения: все потоки отследены (100%)

### 3. **Метрики производительности (Performance Metrics):**
- Задержка классификационного движка: < 5 секунд на 100K строк
- Пропускная способность ETL: > 1M строк/час после классификации
- Эффективность хранилища: коэффициент сжатия (целевое значение: 3:1 исходные→DW)

### 4. **Метрики безопасности (Security Metrics):**
- Обнаруженные попытки несанкционированного доступа: 0 (под контролем)
- Соответствие ротации ключей шифрования: 100% в квартал
- Полнота журнала аудита: 100% (WORM хранилище)

## Масштабируемость (план расширения возможностей):

### Текущий объём (1-й год):
- ~350K пациентов
- ~10M медицинских записей
- Прирост данных: 100GB/месяц
- Ежедневный ETL: 2-3 часа в нерабочее время

### Стратегия расширения масштабов:

| Уровень роста | Решение | Сроки |
|---------------|---------|--------|
| **100K → 500K пациентов** (1 год) | Горизонтальное масштабирование ETL (параллельные разделы), шардирование DW | Встроено в архитектуру |
| **500K → 2M пациентов** (2 года) | Мультирегиональный DW (например, Snowflake мультикластер), региональное соответствие GDPR | Расширение на этапе 2 |
| **2M+ пациентов** (3+ года) | Федеративная аналитика (несколько DW по регионам), потоковая передача в реальном времени (Kafka) | Будущая итерация |

### Архитектурные решения для расширения масштабов:
1. **Stateless движок:** Правила классификации можно параллелизировать на Apache Spark
2. **Инкрементальная загрузка:** Только новые/изменённые данные обрабатываются (Delta Lake)
3. **Слой кеширования:** Redis для правил классификации (не переоценивать каждый раз)
4. **Асинхронная обработка:** Медленные трансформации (ML-based оценивание) в фоновой работе
