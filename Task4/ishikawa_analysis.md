# Task 4: Ishikawa анализ узких мест при миграции системы Медикаменте

## ЧАСТЬ 1: Ситуационный анализ

### 1.1 Текущее состояние (As-Is)

**Характеристики:**
- Файловая база (Excel, сетевые диски)
- Ручная синхронизация между 1C системами
- Монолитная архитектура (нет микросервисов)
- Без шифрования и RBAC
- Без audit logs
- Одна база данных для всех операций
- Интеграция с 1C через файлы (batch процессы)

**Проблемы:**
- Низкая масштабируемость
- Отсутствие безопасности
- Долгие cycle time изменений
- Ручные ошибки при синхронизации

### 1.2 Целевое состояние (To-Be)

**Характеристики:**
- PostgreSQL центральная БД + Read Replica + Backup
- 7 микросервисов (Patient, Appointment, Medical Records, Payment, Inventory, Lab, Notification)
- API Gateway (Kong) + IAM (Keycloak)
- Полное шифрование (AES-256 at-rest, TLS 1.3 in-transit)
- Immutable audit logs (WORM)
- Message Queue (RabbitMQ/Kafka) для асинхронности
- Analytics Layer (Snowflake, Airflow, Tableau)
- Kubernetes orchestration
- Observability (ELK, Prometheus, Jaeger, Splunk SIEM)

**Цели миграции:**
- Поддержка роста на 5x (масштабируемость)
- Безопасность (Privacy by Design, 152-ФЗ, PCI DSS compliance)
- Аналитика (BI, data-driven decisions)
- Надёжность (99.5% uptime, disaster recovery)
- Скорость разработки (independent deployments)

## ЧАСТЬ 3: Детальный анализ узких мест

### **КАТЕГОРИЯ 1: ИНФРАСТРУКТУРА (Infrastructure)**

#### 1.1 Сетевая пропускная способность
Проблема: Текущая сеть (1 Gbps) не соответствует требованиям микросервисной архитектуры
Причины:
 - Много service-to-service вызовов (REST, gRPC, mTLS)
 - Реплика БД требует потоковой репликации (WAL streaming)
 - Логи аудита требуют отправки в SIEM (real-time)
 - Аналитика требует экспорта данных (ETL)
 - Резервная копия требует пропускной способности для 100GB+ данных
Риск: Сетевые задержки (latency > 200ms), потери пакетов
Влияние: Замедление критичных операций (платежи, диагнозы)
Рекомендация: Upgrade до 10 Gbps + ExpressRoute/DirectConnect

#### 1.2 Серверная инфраструктура
Проблема: Текущая серверная инфраструктура не соответствует требованиям микросервисов и новых компонентов
Риск: Ошибки нехватки памяти (out of memory errors), ограничение CPU (CPU throttling), завершение pods в Kubernetes (OOMKilled pods)
Влияние: Недоступность сервиса (критичные алерты, простой для клиентов)
Рекомендация: Аренда дополнительных серверов + облачные резервные мощности (Cloud burst capacity)

#### 1.3 Хранилище данных (Storage)

Проблема: Объём хранилища недостаточен
Причины:
 - Data Warehouse требует многолетнего хранения
 - Логи Elasticsearch требуют 30 дней хранения
 - Резервная копия требует 30 суток
 - Данные пациентов растут
 - Реплика БД требует отдельного диска (failover)
Риск: Ошибки переполнения диска (Disk full errors), краши сервиса, повреждение данных
Влияние: Потеря данных, жалобы клиентов, штрафы регуляторов
Рекомендация: Миграция на S3-совместимое облачное хранилище + локальный SSD кеш


#### 1.4 Отказоустойчивость и backup

Проблема: Текущий режим резервной копии (одна полная копия в день) недостаточен
Причины:
 - Нет WAL archiving (восстановление в момент времени невозможно)
 - Резервная копия хранится локально (уязвима к физическому отказу)
 - Нет географической избыточности (один центр данных)
 - Recovery time objective (RTO) слишком долгий
 - Recovery point objective (RPO) слишком долгий
 - Нет протестированных процедур восстановления
Риск: RTO=4ч, RPO=24ч; недостаточно для критичной системы
Влияние: Потеря до 24 часов данных, 4+ часа простоя
Рекомендация: WAL archiving, географически избыточная S3 резервная копия, RTO<30мин RPO<5мин


#### 1.5 Виртуализация и Kubernetes

Проблема: Нет контейнеризации/Kubernetes; миграция требует полной переархитектуры инфраструктуры
Причины:
 - Текущая система = bare metal + VM (ручное развёртывание)
 - Kubernetes требует главные узлы (3x высокая доступность), рабочие узлы (≥3x), кластер etcd
 - Наложение сети (Calico, Flannel) требует переконфигурации сети
 - Нет конвейера CI/CD для автоматизированного развёртывания
Риск: Неудачные развёртывания, простои кластера, проблемы с планированием pods
Влияние: Более длительное время выхода на рынок, повышенная операционная нагрузка
Рекомендация: Начать пилот K8s на 2-3 промежуточных серверах, нанять эксперта K8s

### **КАТЕГОРИЯ 2: ПРОГРАММНОЕ ОБЕСПЕЧЕНИЕ (Software)**

#### 2.1 Миграция базы данных (Database Migration)

Проблема: Переход с Excel/1C файловой системы на PostgreSQL + encryption
Причины:
 - Шифрование данных требует переувеличения хешей всех ПИИ (ФИО, телефон и т.д.)
 - Данные из 100+ файлов Excel требуют нормализации (очистка, валидация)
 - Двойной ввод данных во время параллельного запуска (проблемы синхронизации данных)
 - Отсутствие внешних ключей в Excel → потерянные записи при миграции
 - Зашифрованные поля требуют интеграции Vault (зависимость)
 - Отслеживание истории (логи аудита) требуют переработки (нет логов аудита в Excel)
Риск: Потеря данных, повреждение, нарушения целостности ссылок
Влияние: Пациенты не могут записаться, врачи видят повреждённые данные, платежи дублируются
Рекомендация: Конвейер ETL (Python + Apache Airflow), проверка миграции 10 раз


#### 2.2 Микросервисная архитектура

Проблема: 7 новых микросервисов требуют нового стека и паттернов
Причины:
 - Service-to-service взаимодействие требует обработки ошибок (circuit breaker, повторные попытки)
 - Распределённые транзакции требуют паттерна Saga (нет гарантий ACID между сервисами)
 - Нет межсервисного тестирования (mock сервисы?)
 - Мониторинг становится сложнее (N сервисов × M экземпляров = N×M логов для анализа)
 - Операционная нагрузка: каждый сервис = отдельное развёртывание, логи, метрики
 - Message Queue (RabbitMQ/Kafka) требует нового операционного знания
Риск: Несогласованные данные между сервисами, каскадные отказы
Влияние: Пациент записывается на приём, но врач этого не видит, платежи теряются
Рекомендация: Записи решений архитектуры (ADRs), инженерия хаоса, каталог сервисов


#### 2.3 API Gateway (Kong) развёртывание

Проблема: Текущая архитектура = прямой доступ к backend; Kong требует переконфигурации
Причины:
 - Отсутствует ограничение частоты запросов (система легко перегружается)
 - Kong требует управления конфигурацией (Kong Admin API vs файлы конфигурации)
 - Выбор плагинов (аутентификация, логирование, ограничение частоты) требует тестирования
 - Сертификаты mTLS требуют ротации (каждые 90 дней)
 - Kong также требует высокую доступность (минимум 2 узла)
 - Миграция требует развёртывания без простоев (сложно)
Риск: API Gateway становится единой точкой отказа
Влияние: Весь трафик заблокирован если Kong упал; ограничения частоты убивают batch клиентов
Рекомендация: Kong высокая доступность + балансировщик нагрузки + circuit breaker + fallback


#### 2.4 Очередь сообщений (Message Queue) (RabbitMQ/Kafka)

Проблема: Система требует асинхронной коммуникации через очередь сообщений
Причины:
 - Текущая = только синхронная (все вызовы блокируют до ответа)
 - RabbitMQ требует кластеризации (3+ узлов для высокой доступности)
 - Порядок сообщений не гарантирован между разделами (Kafka)
 - Доставка ровно один раз сложно достичь (часто минимум один раз)
 - Мёртвые очереди для неудачных сообщений (операционная нагрузка)
 - Отсутствует идемпотентность в текущих сервисах (дублирующиеся сообщения = дублирующиеся записи)
 - Обработка обратного давления (что если очередь переполнится?)
Риск: Потеря сообщений, дубликаты, обработка не по порядку
Влияние: Дублирующиеся приёмы, платежи обработаны дважды, уведомления не отправлены
Рекомендация: Ключи идемпотентности во всех сообщениях, framework доставки ровно один раз, мониторинг


#### 2.5 Безопасность и шифрование

Проблема: Текущая система = нет шифрования; To-Be требует AES-256 везде
Причины:
 - Шифрование уровня поля медленнее (проблемы поиска)
 - Vault требует операционного знания (ротация ключей, управление секретами)
 - Зашифрованные данные требуют изменение схемы (размер поля ФИО увеличится на 20%)
 - Влияние производительности: шифрование/расшифровка при каждом запросе
 - Сложность управления ключами (ключ на пациента? на поле? на роль?)
 - УКЭП цифровые подписи требуют интеграцию HSM (аппаратный модуль безопасности)
 - PCI DSS требует токенизации (не хранение card data без защиты)
Риск: Нарушения данных, штрафы регуляторов
Влияние: Потеря доверия клиентов, приостановление лицензии
Рекомендация: Vault с backend HSM, шифрование уровня поля только для ограниченных данных

### **КАТЕГОРИЯ 3: ИНТЕГРАЦИЯ И ДАННЫЕ (Integration & Data)**

#### 3.1 Интеграция с 1C Бухгалтерия

Проблема: 1C работает в файловом режиме; интеграция требует синхронизации на основе API
Причины:
 - Текущий: batch файлы (1-2 раза в день) → задержка в 12+ часов
 - To-Be требует real-time синхронизацию (или квази real-time каждый час)
 - 1C может работать в сетевом режиме, но требует лицензию
 - Интеграция API требует обработки ошибок (что если API 1C упал?)
 - Согласованность данных: платёж в Медикаменте vs платёж в 1C (могут не совпасть)
 - Задержки при синхронизации (модель eventual consistency требуется)
 - Параллельный запуск (старая+новая система) требует двойного ввода
Риск: Несоответствие данных, дублирующиеся платежи, потеря доходов
Влияние: Пациент заряжен дважды, бухгалтер видит несогласованные отчёты
Рекомендация: Гибридная интеграция (batch + real-time), задача сверки, trail аудита


#### 3.2 Интеграция с 1C Торговля (Инвентарь)

Проблема: Товарное движение требует синхронизации в реальном времени (рост 5x)
Причины:
 - Текущий: синхронизация 2 раза в день (ручной batch)
 - Рост 5x = 10,000+ товарных движений/день → требует real-time
 - Уровни товара могут стать отрицательными (overshoot при параллельном запуске)
 - Нет распределённых блокировок (distributed locks) в текущей системе
 - Алерты переупорядочивания требуют автоматизации (когда заказывать новый товар?)
 - 1C + Медикаменте = два источника истины
Риск: Перепродажа товара, нехватка товара, каскадные отказы
Влияние: Врач заказывает лекарство но его нет; пациент ждёт
Рекомендация: Event-sourcing для товарных движений, паттерн saga для распределённых транзакций


#### 3.3 Интеграция с лабораторией (внешний API)

Проблема: Лаборатория = внешний API; требует доверия и безопасности
Причины:
 - Текущая: ручные заказы по телефону/email
 - Интеграция API требует: аутентификация (API key), шифрование (TLS + mTLS)
 - Лаборатория может быть недоступна (требуется fallback = ручные заказы)
 - ПИИ требуется маскирована при отправке в лабораторию
 - Результаты анализов требуют проверки подлинности
 - SLA с лабораторией требует мониторинга
Риск: Недоступность сервиса, утечка данных, неправильные результаты
Влияние: Задержана диагностика, здоровье пациента под угрозой, ответственность
Рекомендация: API gateway для интеграции лаборатории, circuit breaker, валидация результатов


#### 3.4 Интеграция Data warehouse (Аналитика)

Проблема: Миграция данных в Data Warehouse требует конвейер ETL
Причины:
 - Snowflake/BigQuery требуют определение схемы (схема OLTP ≠ схема DW)
 - Маскирование ПИИ требует правил (что маскировать для роли analyst?)
 - Исторические данные требуют разделение (по дате, по пациенту)
 - Real-time vs batch: медицинские данные требуют quasi-real-time (1 час задержки приемлемо)
 - Качество данных: OLTP может иметь плохие данные (null значения, несоответствия)
 - Медленно меняющиеся размеры (SCD): как обновить прошлые данные? (SCD Type 2)
 - Безопасность уровня строк в инструменте BI требует конфигурацию (Tableau/PowerBI RLS)
Риск: Аналитик получает неправильные данные
Влияние: Неправильные бизнес-решения, упущенные возможности роста
Рекомендация: Тесты качества данных, dbt для трансформаций, медленные добавочные загрузки


#### 3.5 Синхронизация данных во время параллельного запуска

Проблема: Параллельный запуск (As-Is + To-Be) требует двусторонней синхронизации
Причины:
 - Пациент зарегистрирован в Excel (As-Is) → нужно синхронизировать в PostgreSQL (To-Be)
 - Приём создан в To-Be → нужно синхронизировать в Excel (As-Is видит обновлённое расписание)
 - Обновления идут из обеих систем (разрешение конфликтов eventual consistency)
 - Временные окна синхронизации (каждый час?) могут привести к потерям
 - Если синхронизация остановится → какая система источник истины?
 - Данные могут разойтись
Риск: Расходящиеся данные, потерянные обновления, пациент видит устаревшую информацию
Влияние: Пациент записывается в To-Be но видит старое расписание в As-Is; путанница
Рекомендация: Event sourcing, типы данных, свободные от конфликтов (CRDTs), trail аудита

### **КАТЕГОРИЯ 4: ПЕРСОНАЛ (People)**

#### 4.1 Отсутствие опыта с микросервисной архитектурой

Проблема: Текущая команда работает с монолитной структурой;
Причины:
 - Разработчики привыкли к синхронным вызовам (REST); асинхронные паттерны новые
 - Отладка распределённых систем сложнее (логирование, трассировка требуются)
 - Развёртывание = нет blue-green, нет canary; To-Be требует продвинутые стратегии
 - Операционная сложность
 - Нет фона инженерии хаоса (тестирование отказоустойчивости системы)
Риск: Плохо спроектированные сервисы, операционные ошибки, долгое MTTR (среднее время восстановления)
Влияние: Медленное развёртывание функций, частые простои
Рекомендация: Обучение микросервисам


#### 4.2 Отсутствие опыта с Data Engineering / ETL

Проблема: To-Be требует Data Warehouse + ETL; текущей команды нет data engineer
Причины:
 - Нет опыта Airflow / dbt
 - Snowflake / BigQuery требуют специализированного знания
 - Маскирование ПИИ требует тщательного проектирования
 - Проверки качества данных требуют тестирования (отличается от обычного unit тестирования)
 - Нет опыта моделирования данных (star schema, dimensional modeling)
Риск: Сломанные задачи ETL, повреждение данных, неправильные отчёты
Влияние: Аналитики не могут выполнять анализ, BI дашборды показывают мусор
Рекомендация: Обучение Airflow/dbt, best practices моделирования данных


#### 4.3 Отсутствие опыта с Безопасностью / Compliance

Проблема: 152-ФЗ + PCI DSS требуют expertise безопасности; текущая команда = нет training безопасности
Причины:
 - Шифрование, Vault, HMAC = новые концепции
 - Проектирование RBAC/ABAC = не straightforward
 - Логирование аудита требует знание compliance
 - Тестирование проникновения, сканирование уязвимостей = не выполняется
 - Нет champion безопасности в команде
Риск: Нарушения безопасности, штрафы регуляторов, потеря данных
Влияние: Компания теряет лицензию, клиенты теряют доверие, финансовая катастрофа
Рекомендация: Нанять консультант безопасности, CISO как советник, training безопасности для всех

### **КАТЕГОРИЯ 5: ПРОЦЕССЫ (Processes)**

#### 5.1 Отсутствие процесса миграции данных

Проблема: Нет четкого процесса для миграции
Причины:
 - Валидация данных
 - Очистка данных
 - Обнаружение дубликатов
 - Откат миграции
 - Миграция без простоев
 - Тестирование
Риск: Повреждение данных, потеря данных, несоответствия
Влияние: Записи пациентов неправильные, история болезни потеряна, ответственность
Рекомендация: Playbook миграции, тестирование миграции 10 раз, dry-run с реальными данными (анонимизированные)


#### 5.2 Отсутствие процесса тестирования в микросервисной архитектуре

Проблема: Текущее тестирование = ручное; To-Be требует автоматизированное тестирование
Причины:
 - Unit тесты: каждый сервис имеет свои тесты
 - Integration тесты: как тестировать взаимодействие между сервисами?
 - Contract тестирование: как убедиться, что контракты API не нарушены?
 - E2E тесты
 - Инженерия хаоса: как тестировать отказоустойчивость при injection сбоев?
 - Тесты производительности: как обеспечить compliance SLA?
Риск: Дефектные развёртывания, runtime сбои, нарушения SLA
Влияние: Пациенты не могут записаться, работа врачей прервана, потеря доходов
Рекомендация: Пирамида автоматизации тестов, contract тестирование, инженерия хаоса


#### 5.3 Отсутствие процесса CI/CD

Проблема: Текущее развёртывание = ручное; To-Be требует continuous deployment
Причины:
 - Нет CI сервера (Jenkins, GitLab CI, GitHub Actions)
 - Нет автоматизированных тестов в pipeline (все ручные)
 - Развёртывания = ручное копирование-вставка файлов (подверженные ошибкам)
 - Откат = ручной revert
 - Нет blue-green развёртываний (развёртывания без простоев невозможны)
 - Release notes = не поддерживаются
Риск: Медленные развёртывания, высокий процент ошибок, долгое MTTR
Влияние: Функции развёртываются неделями, баги исправляются днями
Рекомендация: GitLab CI / GitHub Actions, blue-green развёртывания, автоматизированные откаты


#### 5.4 Отсутствие процесса мониторинга и оповещения

Проблема: Текущий мониторинг = ручные проверки; To-Be требует автоматизированный мониторинг
Причины:
 - Нет сбора метрик (Prometheus)
 - Нет централизованного логирования (ELK stack)
 - Нет правил оповещения
 - Нет мониторинга SLA
 - Нет распределённой трассировки (Jaeger)
 - Процесс on-call = неформальный
Риск: Проблемы не обнаруживаются пока не пожалуется клиент
Влияние: Долгое время ответа на инцидент (2+ часа), репутационные потери
Рекомендация: Prometheus + Grafana, ELK stack, Splunk SIEM, ротация on-call


#### 5.5 Отсутствие процесса восстановления после бедствия (disaster recovery)

Проблема: Текущая DR = резервная копия один раз в день; To-Be требует RTO < 30 мин, RPO < 5 мин
Причины:
 - Нет протестированной процедуры DR
 - Резервная копия хранится локально
 - Нет географической избыточности
 - Шаги восстановления не документированы
 - Нет механизма failover
 - Нет регулярных упражнений DR
Риск: Долгое время простоя (4+ часа), потеря данных (24+ часа)
Влияние: Непрерывность бизнеса нарушена, нарушения регуляторов, банкротство
Рекомендация: Мультирегион setup, автоматизированный failover, ежемесячные упражнения DR


#### 5.6 Отсутствие процесса управления конфигурацией

Проблема: Конфигурация разбросана; To-Be требует configuration-as-code
Причины:
 - Database конфигурация = в файле конфигурации PostgreSQL (ручные изменения)
 - Application конфигурация = hardcoded в приложении (требует перекомпиляцию для изменений)
 - Network конфигурация = ручные правила Firewall (не документированы)
 - Нет version control для конфигурации (нет trail аудита)
 - Нет разделения окружений (dev vs staging vs prod конфигурации)
 - Нет управления секретами (пароли в plaintext)
Риск: Configuration drift, несоответствие окружений, нарушения безопасности
Влияние: Увеличивается разрыв между dev и prod, ошибки при ручных изменениях, утечка секретов
Рекомендация: Configuration-as-code (Terraform, Ansible), секреты в Vault, GitOps

### **КАТЕГОРИЯ 6: SECURITY (Безопасность)**

#### 6.1 Шифрование на уровне приложения

Проблема: Текущая система = нет шифрования; To-Be требует AES-256 везде
Причины:
 - Влияние производительности: шифрование/расшифровка замедляет запросы
 - Шифрование уровня поля усложняет поиск
 - Управление ключами: где хранить ключи? Как ротировать?
 - Compliance 152-ФЗ
 - Тестирование: как тестировать зашифрованные данные?
Риск: Нарушение данных, штрафы регуляторов
Влияние: Потеря доверия клиентов, урон репутации
Рекомендация: Шифрование уровня поля только для ограниченных данных, Vault для управления ключами


#### 6.2 Аутентификация и авторизация

Проблема: Текущая система = нет RBAC; To-Be требует строгий контроль доступа
Причины:
 - Keycloak = новая система IAM (конфигурация, setup realm, mappers)
 - Проектирование RBAC требует тщательного рассмотрения (что роль пациента vs роль врача?)
 - ABAC (на основе атрибутов) ещё более сложный (врач может получить доступ только к своим пациентам)
 - Управление token: JWT, refresh токены, expiry токена
 - Single sign-on требует конфигурацию client приложения
 - Наследование permission (если роль меняется, какие permissions обновляются?)
Риск: Несанкционированный доступ, эскалация privilege
Влияние: Врач видит медицинские записи других пациентов (массивная ответственность)
Рекомендация: Setup Keycloak с RBAC/ABAC, регулярные проверки доступа, модель zero-trust


#### 6.3 Сетевая безопасность (Network security)

Проблема: Текущая сеть = нет сегментации; To-Be требует архитектуру zero-trust
Причины:
 - Сегментация VPC: отдельные подсети для разных уровней (web, app, db)
 - Security groups: правила ingress/egress на сервис
 - mTLS между сервисами: требует управление сертификатами
 - WAF: защита от SQL injection, XSS атак
 - DDoS защита: CloudFlare или AWS Shield
 - VPN: доступ админа только через зашифрованный tunnel
Риск: Атаки уровня сети, боковое движение атакующего
Влияние: Полный компромисс системы, все данные пациентов раскрыты
Рекомендация: Setup VPC, security groups, WAF, mTLS, регулярное тестирование проникновения


#### 6.4 Логирование аудита и compliance

Проблема: Текущая система = нет логов аудита; To-Be требует immutable логи для 152-ФЗ
Причины:
 - Таблица immutable audit log (WORM = write-once, read-many)
 - Каждая операция залогирована: пользователь, действие, timestamp, результат, fingerprint данных
 - Подписи HMAC для целостности (как проверить что log не был изменён?)
 - 7-летнее хранение (где хранить такой объём? S3?)
 - Влияние производительности: логирование аудита должно быть async (не блокировать приложение)
 - Проверка compliance: как доказать compliance регулятору?
Риск: Нарушения регуляторов, нет доказательств для расследований
Влияние: Штрафы до 5M RUB, приостановление лицензии
Рекомендация: WORM хранилище, подписи HMAC, асинхронное логирование, регулярные audit compliance


#### 6.5 Приватность по проектированию (Data privacy by design)

Проблема: Privacy-by-design требует fundamental переосмысления; текущая система = нет приватности
Причины:
 - Минимизация данных: собирать только необходимые данные (какие данные действительно необходимы?)
 - Управление согласием: явный opt-in для сбора данных
 - Право быть забытым: GDPR требует удаления данных по запросу (как удалить зашифрованные данные?)
 - Портативность данных: пациент хочет получить свои данные
 - Уведомление о нарушении: если data breach, нужно notify пациентов в 72 часа
 - Оценка влияния приватности (PIA): требуется перед обработкой ПИИ
Риск: Нарушения приватности, штрафы GDPR
Влияние: Потеря доверия клиентов, регуляторное действие
Рекомендация: Политика приватности, формы согласия, политики хранения данных, training приватности
